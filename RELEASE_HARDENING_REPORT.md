# Zoe CLI Release Hardening Audit

## Scope and current verdict

This audit covers the planner, task routing, runtimes, tool-call parsing, tool dispatch, permissions, filesystem persistence, verification, repair, authentication, summaries, package entry points, and npm bundle. Zoe is **not release ready** in the current architecture because more than one execution system can decide task state and several mandatory failure paths are not covered by tests.

## Current execution paths

### Chat path

- `src/cli/commands/chat.ts` routes greetings and analysis to `runAgent`.
- `runAgent` in `src/core/agent.ts` calls the cloud model, parses XML and JSON-like tool calls in `processToolCalls`, executes tools, then asks the model for follow-up prose.
- This path can write files even though it has no authoritative structured plan or Runtime-owned final state.

### Structured task path

- `chat.ts` calls `createPlan`, which asks the model for JSON and validates it with `executionPlanSchema`.
- Only one hard-coded React/Vite/TypeScript request shape enters `executeGoldenPathRuntimeV2`.
- The golden path uses `RuntimeController`, a second tool-call parser (`processGoldenFileCalls`), objective requirements, and one build command.

### Legacy task path

- Every task not matching the golden-path predicate enters `executePlan`.
- `executePlan` converts structured JSON back into the legacy `ExecutionRuntime` shape, retains free-form/Markdown extraction helpers, runs a separate execution loop, performs separate validation, and uses an LLM reviewer.
- `src/core/execution-runtime.ts` and `src/core/runtime-controller.ts` independently model execution state and completion.

### Other entry points

- `src/cli/commands/run.ts` calls `runAgent` directly and bypasses structured task execution.
- CLI startup is `src/cli/index.ts`; npm exposes `dist/cli/index.js` through the `zoe` bin.

## Duplicated and conflicting logic

- Two runtime state implementations: `ExecutionRuntime` and `RuntimeController`.
- Two task executors: `executePlan` and `executeGoldenPathRuntimeV2`.
- Two tool parsers: `processToolCalls` and `processGoldenFileCalls`.
- XML and JSON parsing are implemented independently rather than normalized once.
- Structured JSON plans coexist with legacy Markdown and regex extraction.
- File counts exist both in local counters and runtime state.
- Build status is inferred from warning text in the legacy path and stored as evidence in the V2 path.
- The model owns `userConstraints` inside the plan, allowing it to weaken the original request.
- Read caching exists in the general agent path but is not a task-scoped runtime service.

## Root causes

1. Runtime V2 was introduced alongside the legacy executor rather than becoming the sole task authority.
2. User constraints are generated by the LLM instead of deterministically extracted and attached by the Runtime.
3. The golden-path selector couples reliable execution to one prompt instead of task semantics.
4. Tool-call formats are parsed inside executors, producing divergent behavior and missed calls.
5. Tool results are strings, so callers infer success from prefixes instead of consuming typed evidence.
6. Permission handling returns false immediately for invalid input and cannot distinguish denial from unavailable input.
7. Authentication validates local profile presence but does not provide a centralized refresh-and-retry wrapper for every AI request.
8. Verification and review mix filesystem evidence, warning text, and model prose.
9. Test coverage is a single script with no injectable model, permission, auth, command, or filesystem boundaries.

- Planning and orchestration: `src/core/agent.ts`, `src/core/prompt.ts`, `src/cli/commands/chat.ts`, `src/cli/commands/run.ts`.
- Plan and state: `src/core/execution-plan.ts`, `src/core/runtime-controller.ts`, `src/core/execution-runtime.ts`.
- Tools and safety: `src/core/tools.ts`, `src/core/workspace.ts`, `src/core/permissions.ts`, `src/core/backups.ts`.
- Authentication/cloud: `src/core/insforge.ts`, `src/core/auth.ts`, `src/core/config.ts`.

- Packaging: `package.json`, `src/cli/index.ts`, generated `dist/`.
- Tests: `test/workspace.test.ts`.

## Migration strategy

1. Introduce Runtime-owned `UserIntent` and `UserConstraints`; extract them before calling the planner and never accept model-authored constraints.
2. Expand `ProjectSnapshot` deterministically and make it the planner's only source for known project facts.
3. Version the structured plan, remove `userConstraints` from model output, attach constraints after parsing, and reject Markdown/free-form plans.
4. Add one boundary normalizer that converts provider, JSON, and temporary XML calls into `NormalizedToolCall`.
5. Add one typed tool executor that validates, requests permission, executes, verifies persistence/exit status, invalidates cache, and updates Runtime state.
6. Route every mutating or command-running request to one Runtime task path; keep chat mode read-only and independent per message.
7. Replace text-based verification with stored requirement and validation evidence. Keep reviewer prose advisory only.
8. Add centralized cloud session refresh and one retry for `AUTH_UNAUTHORIZED` without losing execution state.
9. Isolate then delete the legacy runtime, Markdown parsing, special React selector, and duplicate executor after parity tests pass.
10. Run unit, integration, temporary-directory E2E, `npm pack --dry-run`, packed install, and clean-login validation before release approval.

## Required tests

- Deterministic constraint extraction and canonical path resolution.
- Planner cannot weaken constraints; one repair only; invalid repaired plan stops safely.
- Snapshot detection for empty, React/Vite/TS, package managers, monorepos, scripts, dependencies, and Git state.
- JSON/XML/provider tool normalization into one representation.
- Tool schema validation, permission outcomes, write/edit persistence, cache invalidation, and immediate state updates.
- Build execution exactly once, repair reruns, objective requirement evidence, and no false success.
- Permission parser acceptance, invalid-input reprompt, denial state, and session-scoped always approval.
- Auth refresh, one retry, unrecoverable login guidance, and preserved completed writes.
- Chat/task classification and no implicit continuation after casual messages.
- Seven required E2E scenarios and clean packed installation.

## Risks and mitigations

- **Behavior regression while removing legacy paths:** use a temporary compatibility boundary, then disable legacy task execution only after Runtime integration tests pass.
- **Overly broad natural-language constraint parsing:** extract only explicit restrictions deterministically; ambiguous restrictions produce `NEEDS_USER_INPUT`.
- **Cross-platform command differences:** use package-manager-aware argument arrays and temporary tests; do not claim unsupported platforms.
- **Permission deadlocks in non-interactive environments:** return a typed user-input requirement instead of silently denying.
- **Model tool-format variation:** normalize all accepted boundary formats before validation and execution.
- **Auth SDK variation:** isolate session refresh behind a small adapter and test with injected responses.
- **Destructive writes during tests:** use temporary workspaces and injectable permission decisions.

## Package audit baseline

`package.json` publishes `dist`, `README.md`, `LICENSE`, and `.env.example`; `prepack` rebuilds TypeScript. The baseline still requires `npm pack --dry-run`, tarball-content inspection, packed installation, entry-point checks, and verification that `.env.example` actually exists. Current metadata claims Node `>=18` and does not restrict operating systems, so cross-platform behavior must be tested or documented honestly.

## Release gate

Do not publish or declare release readiness until the authoritative Runtime handles all coding tasks, all mandatory automated tests pass, all seven E2E scenarios pass, packed installation and login are verified, and documentation matches observed platform support and limitations.
